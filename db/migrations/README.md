# db/migrations

Prisma migration history (Blueprint §7.6). The first migration
establishes the seven bounded-context schemas (Blueprint §7.2), Row-Level
Security policies (§7.3), the append-only Financial Transaction event log
(§7.4), and the temporal GROUP_MEMBERSHIP model (§7.5).

**Status (Sprint 1.3): fully verified - applied to a real PostgreSQL
instance, `prisma migrate diff` against it comes back empty, and
`pnpm db:seed` succeeds.**
`20260801000000_init_bounded_context_schemas/migration.sql` was
hand-written to match `db/schema.prisma`, not generated by `prisma
migrate dev` - the sandbox that authored it had no database or package
registry access. Applying it for real against a local Postgres surfaced
four real gaps between the SQL and `schema.prisma`, each closed by its own
follow-up migration rather than by editing the already-applied file
(editing an applied migration.sql breaks Prisma's checksum tracking - see
the note below, learned the hard way once during this process):

1. `20260801010000_rename_indexes_to_match_prisma_convention` - 7 indexes
   whose hand-picked names didn't match Prisma's default naming convention.
2. `20260801020000_drop_updated_at_column_defaults` - the hand-written SQL
   gave `updated_at` a `DEFAULT now()`; Prisma's `@updatedAt` manages that
   column entirely client-side and doesn't expect a DB default.
3. `20260801030000_normalize_foreign_key_on_update_cascade` - the
   hand-written SQL never specified `ON UPDATE` on any foreign key
   (Postgres defaults to `NO ACTION`); Prisma's implicit default is
   `CASCADE`. Inert in practice (primary keys here are immutable UUIDs)
   but fixed for full parity.

(A fourth gap - missing `@db.Timestamptz` on `DateTime` fields and a
missing `@default([])` on `role_assignments.scope_group_ids` - was on the
`schema.prisma` side, not the SQL side, and didn't need its own migration.)

See `db/DESIGN_NOTES.md` for exactly which parts of the schema are
`[BLUEPRINT-EXACT]` (shown verbatim in the Blueprint) versus
`[PRD-DERIVED]` (table named in the Blueprint, columns inferred from a
cited PRD requirement), the corrections made from the pre-Blueprint first
draft, and the open questions that remain genuinely unresolved.

**Do not edit a migration.sql file after it has been applied.** Prisma
records a checksum of each migration when it's applied; editing the file
afterward (rather than adding a new migration) causes `prisma migrate
dev`/`status` to flag it as tampered. This happened once during Sprint
1.3's verification - a set of index-rename edits was made directly to the
already-applied first migration, then reverted and moved into the second
migration instead once the mistake was caught.
